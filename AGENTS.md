# Agent Notes for Scribe

A small Bun + TypeScript terminal UI project. Keep it simple.

## What Scribe is

Scribe is (becoming) a bring-your-own-model TTRPG campaign builder and
organizer: users create campaigns for any system, plan sessions with an LLM
agent in a chat-like harness, run sessions from generated markdown notes, then
report outcomes so the agent maintains a running campaign summary it uses to
plan future sessions. **Read `PLAN.md` before making architectural decisions**
— it contains the full design and roadmap.

Locked design decisions (don't revisit without asking):

- **Persistence is markdown-first**: campaign data lives in user-visible
  markdown files with frontmatter (default `~/Scribe`), not a database. The
  files the agent reads/writes are the same files the user owns.
- **Frontmatter is flat `key: value` lines**, parsed by a tiny hand-rolled
  parser — do not add a YAML dependency.
- **Model access is OpenAI-compatible only** (configurable `baseUrl`/`model`,
  covers OpenAI/OpenRouter/Ollama/LM Studio). API keys are referenced by env
  var name in `~/.config/scribe/config.json` — never store keys.
- Current roadmap phase: **roadmap complete (phases 0–6 done)** — see
  `PLAN.md` for deferred/future ideas.

## Project basics

- **Runtime**: Bun (`bun` v1.3+).
- **Entry point**: `src/index.ts`.
- **Only dependencies**: `@opentui/core` (TUI component library) and `unpdf` (PDF text extraction — imported by `src/store/sources.ts` and nowhere else).
- **Tests**: `bun:test` in `tests/`. No lint, formatter, or CI yet. Headless UI tests share `tests/helpers/renderer.ts` (`setupRenderer` + `wait`); destructure it in `beforeEach` so tests keep referring to bare `renderer`/`keys`/`captureCharFrame`/`renderOnce`.

## Common commands

```bash
# Install dependencies
bun install

# Run the app (interactive terminal UI)
bun run src/index.ts

# Watch mode during dev
bun --watch src/index.ts

# Type check (no emit; tsconfig sets "noEmit": true)
bunx tsc --noEmit

# Run tests (store unit tests + headless UI flow test)
bun test
```

## TypeScript / Bun specifics

- `tsconfig.json` targets Bun: `"types": ["bun"]`, `"module": "Preserve"`, `"moduleResolution": "bundler"`, `"noEmit": true`.
- Strict mode is on, including `noUncheckedIndexedAccess` and `noImplicitOverride`.
- Imports use `.ts` extensions (e.g., `./ui.ts`, `./consts.ts`); this is required by `allowImportingTsExtensions`.

## Entrypoints and architecture

- `src/index.ts`: entry point + screen manager. One `Screen` at a time under the renderer root (dispose → remove → destroy → add). Also owns the campaign-create dialog and app-level wiring.
- `src/screens/screen.ts`: `Screen` interface (`node` + optional `focus()`/`dispose()`).
- `src/screens/main-menu.ts`: main menu — create / campaign list (loaded from disk) / quit, plus the intro animation on first show.
- `src/screens/campaign-home.ts`: campaign view — background & story-so-far peeks, session list with statuses, new-session dialog, session detail dialog ("Plan with Agent" for planning sessions, "Report outcome" for ready sessions, mark ready/played, trash), Escape goes back.
- `src/screens/settings.ts`: settings screen — edit base URL, model, API key env var, campaigns dir, one-shots dir, sources dir; persists to config.json via `saveSettings`. "Browse..." opens `model-picker-dialog.ts` over the provider's `/models` listing; a `modalOpen` flag stands the screen's keypress handler down while it is up, so the picker owns Escape (same pattern as `chat.ts`/`campaign-home.ts`).
- `src/screens/chat.ts`: chat screen (harness) — markdown transcript (via `makeTranscript` from `components/transcript.ts`) + prompt (via `makePrompt` from `components/prompt.ts`). Streams assistant replies from any `ChatProvider`; surfaces provider errors as inline transcript notices. There is no status line: what Scribe is doing is recorded as activity rows **in** the transcript (thinking, then one row per tool call, each settling into its past-tense label and elapsed time), driven by `runAgent`'s `onTool`/`onToolEnd` and by the screen's own turn boundaries. `ask_user` deliberately gets no activity row — the question widget and the answered Q&A row already say it. When `tools` is **non-empty** (planning/report/oneshot) sends run through `runAgent`, mirroring its `onMessage` hand-overs into `messages` so the transcript grows *during* the turn (only plain streaming pushes an empty assistant placeholder to stream into); when omitted or empty, plain streaming with `systemPrompt` prepended to a local copy. With a `chatLog` store it **resumes** the conversation. With an `ask` channel it answers `ask_user`: the question widget takes the prompt box's slot until the user picks (Escape dismisses the question, not the screen), and answered questions surface in the transcript by **deriving** which tool results came from `ask_user` (collecting call ids off the assistant messages' `tool_calls`) rather than stamping a field on `ChatMessage` — so the wire format and the JSONL log are untouched and resumed conversations render with no migration; dismissed questions render nothing. Also owns a completion popup over the prompt: the `/` commands (`/clear`, `/back`) are built in because they act on the chat rather than the message, while `@` sources arrive via `completions` so the screen stays ignorant of the store. `/clear` confirms via `showConfirmDialog` and is refused while the agent is busy; a `modalOpen` flag stands the screen's keypress handler down so the dialog owns Escape (same pattern as `campaign-home.ts`). One keypress listener, routed question widget → popup → Escape.
- `src/components/`: reusable UI widgets (opencode-style).
  - `ui.ts`: shared primitives — focusable/mouse-aware buttons (`makeButton`, click + Enter), Tab/Shift+Tab focus traversal (`tabWalk`), and `enableSelectMouse` (hover/click/wheel for `SelectRenderable` menus). `SelectRenderable` draws its rows into one frame buffer instead of child renderables, so `enableSelectMouse` hit-tests a mouse y against the select's own `scrollOffset`/`linesPerItem` — internal fields reached through a cast. Pass its `isEnabled` guard when a modal can sit over the list.
  - `dialog.ts`: generic centered modal primitive (`makeDialog`) — absolute full-screen layer + `zIndex`, toggled via `visible`. Callers handle focus.
  - `action-dialog.ts`: generic modal with a body + button row (`makeActionDialog`) — owns layer lifecycle, Tab/Shift+Tab traversal, Escape-to-close, initial focus; `onClose` returns focus.
  - `confirm-dialog.ts`: `showConfirmDialog` — yes/no confirmation for a destructive action, built on `action-dialog.ts`. Cancel is added first (so the safe choice holds focus) unless `focusConfirm` is set; used by `/clear` in the chat and by trash in `campaign-home.ts`.
  - `form-dialog.ts`: `makeFormDialog` — shared shell for the **persistent** form dialogs (campaign, session), whose layer is created once and shown/hidden rather than destroyed. Owns the open/close keyboard handover (Escape cancels, Tab walks a lazily-read focus chain); callers own fields, buttons, and focus. Contrast `action-dialog.ts`, which builds and destroys a fresh layer per open.
  - `transcript.ts`: `makeTranscript` — the chat transcript column. `sync(messages)` reuses the rows of surviving messages so a streaming reply repaints in place instead of rebuilding the tree on every delta; user messages get the accent-strip panel, assistant replies render as markdown, and settled `ask_user` exchanges render as a quieter Q&A aside. The `ask_user` call ids are cached against the message count, since a delta only mutates the last message's content. Alongside the message rows it holds **pinned** rows the screen puts there directly: `beginActivity(present, past)` opens a dimmed "Scribe is thinking…" row that `finish()` settles into "Thought · 4.3s", and `addNotice(text, tone)` drops a one-off dimmed or danger line (errors, refusals). Consecutive activities stack into one muted-rule block; the next message row closes it. A notice repeated while it is still the tail is dropped, so `/clear` hammered mid-turn doesn't build a column of the same refusal. Both kinds are UI-only — they are not `ChatMessage`s, so nothing reaches the model or the JSONL log and a resumed conversation shows the prose without them. Ordering needs no timestamps: pinned rows always append at the tail and `sync` only reconciles the message entries around them, so a screen must `render()` **before** opening an activity or the row lands above the message that prompted it. Two invariants hold the block structure up: (1) `visibleMessages` hides empty-content messages, which is what lets a turn's announced-empty assistant message pass without closing the block — make empty assistants visible and every tool call lands in a block of its own; (2) surviving message rows never need reordering (`messages` is append-and-truncate, the filter is order-preserving), so `sync` only removes and inserts.
  - `campaign-dialog.ts`: "New Campaign" form (`makeCampaignDialog`) built on `form-dialog.ts`. Name + system `InputRenderable`s + background `TextareaRenderable` + `makeButton` buttons; the shell traps Tab/Shift+Tab/Escape while open. `onSubmit`/`onCancel` callbacks, plus `close()` so an owning screen can release the keyboard on dispose.
  - `session-dialog.ts`: "New Session" form (`makeSessionDialog`), same pattern and same shell, single title field.
  - `prompt.ts`: `makePrompt` — opencode-style prompt widget (accent-bordered panel with a multi-line `TextareaRenderable`: Enter sends, Shift+Enter newline, hint footer). Callers own submission and textarea state.
  - `ask-widget.ts`: `makeAskWidget` — the `ask_user` question panel that takes the prompt box's place while a turn waits on a decision. Same `makeAccentPanel` look as the prompt, deliberately: the bottom of the screen is still "where I answer", it has just changed shape. Option rows are hand-rolled rather than a `SelectRenderable`, which can't do multi-select markers plus a "type your own" row that becomes a textarea. Arrows/digits/Space/Enter/Escape, single- or multi-select, optional free-text answer. Keys are **pushed in** via `handleKey` (returns whether it consumed the key) instead of pulled from its own listener, so the chat screen keeps one keypress handler and stays in charge of what Escape means.
  - `autocomplete.ts`: `makeAutocomplete` — the prompt-anchored completion popup. `CompletionItem` (`label`/`description`/`insert`/`run` — `run` acts on the chat and takes its own text back out), `CompletionSource` (`trigger`/`atStartOnly`/`items(query)`, may be async). Anchoring is the whole trick and is simpler than opencode's: the popup is an absolutely positioned child of the prompt box with `bottom: "100%"`, so its bottom edge sits on the prompt's top edge with zero measurement and zero polling — it re-anchors for free when the prompt grows a line or the list changes height, and being out of flow it **overlays** the transcript instead of squeezing it. Keys arrive through `handleKey`; the textarea keeps focus throughout and the popup is never focusable. Rows are allocated once and refilled (windowed, `maxRows` default 8) so typing doesn't churn the renderable tree; labels are padded to a common width so descriptions align. Substitution is `replaceText` + `cursorOffset` behind a re-entrancy flag, and a generation counter discards superseded async `items()`. Owns `input.onContentChange`.
- `src/agent/`: the harness core (Phase 2).
  - `loop.ts`: `runAgent` — tool-call loop (stream → execute tools → feed back → repeat until a text answer), `AgentTool`. Two budgets: `maxIterations` (default 10) counts **model-driven** turns only — that's the runaway guard — while `HARD_MAX_ITERATIONS` (100) bounds the loop overall. A turn whose tool calls are all `AgentTool.userDriven` doesn't spend the first, because a turn gated on a human keystroke can't spin. `onMessage` is the seam the transcript grows through: every message is handed over **as it is created and by reference** — an assistant message is announced empty before its text streams in, then mutated in place (content, then `tool_calls`) — so a mirroring caller ends up element-identical to `AgentResult.messages` and rebuilds nothing at the end. Without it, an answered `ask_user` would only reach the screen once the model's follow-up had finished streaming. The announced-early assistant message is deliberately **not** in `messages` during the request; an empty assistant turn must not go out to the provider.
  - `ask.ts`: the ask seam — `AskQuestion`/`AskOption`/`AskAnswer`, `AskChannel` (`ask`/`attach`/`available`), `makeAskChannel`, `formatAskResult`/`parseAskResult`, `ASK_DECLINED`, `ASK_USER_TOOL_NAME`. A channel because tools are resolved *before* the chat screen exists: the app makes one and passes it to both. `attach` returns a detach function that **settles any in-flight question with `null`** — that is what stops a turn hanging when the user leaves mid-question. The tool result string doubles as the transcript row (`Asked: …` / `Answer: …`), so there is one representation: no JSON parsing in the renderer, and resumed logs render as-is.
  - `agents.ts`: **the gateway** — `AGENTS` maps each agent (`planning` / `report` / `oneshot`) to the tool names it may call, and `toolsFor(agent, ctx)` resolves them. This is the one place to read when auditing what an agent can do. Tool names are checked against the registry at compile time, so a typo is a `tsc` error.
  - `tools/`: one file per tool, each exporting a `ToolSpec` (`name` + `label` + `pastLabel` + `definition` + `create(ctx)`). `label` is the present-tense phrase the transcript's activity row shows while the tool runs ("Reading the session notes…"); `pastLabel` is what that same row settles into when it returns ("Read the session notes · 3.2s"). Both are UI-only and never sent to the model. Resolve them with `toolLabel(name)` / `toolPastLabel(name)` from `tools/index.ts`, which fall back to the raw name.
    - `types.ts`: `ToolContext` (optional `campaign` / `session` / `oneshotsDir` / `sourcesDir` / `defaultSystem` / `ask`) and `ToolSpec`. `create` returns `null` when a tool can't run in the given context — that's how campaign tools drop out of a campaign-less agent, and `ask_user` out of a UI-less one.
    - `index.ts`: the `registry` object literal, `ToolName` (derived from its keys), and `resolveTools(names, ctx)`. Explicit literal, **not** filesystem discovery — that's what makes `ToolName` a compile-time union.
    - `shared.ts`: arg coercion (`stringArg` / `numberArg` / `boolArg`, which tolerates the `"true"`/`"false"` strings models emit for flags) and `findSession` / `freshCampaign`, which re-read from disk so the agent observes its own writes mid-run.
    - Tools: `list-sessions.ts`, `read-campaign-summary.ts`, `read-session-notes.ts`, `update-session-notes.ts`, `append-campaign-summary.ts`, `save-session.ts` (oneshot only — saves a one-shot plan to the one-shots dir; the agent may call it **only on explicit user request**, enforced by the tool description + one-shot prompt wording, not the UI), `ask-user.ts` (granted to **all three** agents — puts a 2–9 option question to the user and blocks the turn on the answer; `userDriven`, and declines when the context carries no `ask` channel).
    - Source-document tools (`list-sources.ts`, `search-sources.ts`, `read-source-pages.ts`), granted to **planning and oneshot but not report** — a write-up of what happened doesn't need the rulebook. All three call `indexSources` first (cheap when the cache is warm) so the agent never reads a stale corpus, and all three decline when the context carries no `sourcesDir`. `search_sources` scopes to `defaultSystem` (the campaign's `system` field) by default; because that field is free text ("D&D 5e") and need not match a Sources folder name ("5e"), a scoped search that finds nothing **widens to the whole library and says so in the result** rather than reporting a miss the user can't diagnose. An explicit `system` argument never widens.
  - `prompts.ts`: `CORE_CAMPAIGN_PROMPT` / `CORE_ONESHOT_PROMPT` — the code-owned core prompts. They live in code, not in a user file, because they carry behavioral contracts (read notes before editing, the plan goes in the notes file, the save_session "only on explicit request" rule); a user file would freeze at whatever version was installed first and silently drop later additions.
  - `context.ts`: `buildPlanningSystemPrompt` / `buildReportSystemPrompt` / `buildOneshotSystemPrompt` — three layers, always in this order: **core** (from `prompts.ts`, or the `systemPromptOverride`/`oneshotPromptOverride` file if configured) → **context** (campaign background/story + sources + session draft or report framing) → **user instructions** (`store/instructions.ts`, appended last so it wins on tone and house rules without being able to delete the tool rules). Each builder takes the whole `Settings` object, since both the override path and `sourcesDir` come from it. Empty sections vanish entirely rather than emitting a header — same convention for `sourcesSection` and `instructionsSection`. Prompts are deliberately **not** owned by the gateway.

  Adding a tool: new file in `tools/` + one line in `tools/index.ts`. Granting it: one string in `agents.ts`. Adding an agent: one entry in `AGENTS` + a prompt builder in `context.ts`.

  **Tool security invariant**: tools never accept filesystem paths from the model. Resources are addressed by identity (session *number*, the active campaign) and resolved through `src/store/`, which is what confines reads and writes to the campaign folder. A future tool needing a path must resolve it internally, not take it as an argument. `read_source_pages` is the worked example: it takes a document *slug or title*, which `src/store/sources.ts` resolves by scanning its index and comparing strings — the model's string is never joined into a path, so `read_source_pages("../../etc/passwd")` simply matches nothing. `ask_user` upholds this trivially — it touches no paths at all — but raises a different consideration: it is the one tool whose result comes from the person rather than the disk, so what the model reads back is only as trustworthy as the UI on the other end of the `AskChannel`, and with no UI attached it declines instead of blocking.
- `src/provider/`: model provider abstraction (Phase 1).
  - `types.ts`: `ChatMessage`, `ToolCall`/`ToolDefinition`, `ChatEvent` (`text` | `tool_call`), `ChatProvider.streamChat(messages, options?)`.
  - `openai.ts`: OpenAI-compatible client (SSE streaming + JSON fallback) and `createProviderFromSettings`. `DEFAULT_BASE_URL`/`DEFAULT_MODEL`.
- `src/theme.ts`: unified palette (`theme`) — burnt-orange accent over flat dark surfaces. ALL UI colors come from here; never hardcode hex literals.
- `src/consts.ts`: ASCII art logos.
- `src/format.ts`: shared display formatting — `formatTokenCount` ("128k") and `formatDollars` (extra precision below a cent), used by the chat model header.
- `src/completions.ts`: the `@`-mention sources handed to the chat screen — `filterCompletions` (case-insensitive over label **and** description, so "@bell" finds the session titled "The Bell Tower"), `sourceItems`/`sourceCompletions` (the PDF library) and `campaignCompletions` (summaries + sessions + sources). Items insert plain-language references ("session 3 (\"The Bell Tower\")") rather than `@slug` markup, because that is what the agent's tools can act on. Resolved per keystroke rather than snapshotted, so sessions added while a chat is open show up. Lives outside `screens/` so it can be tested without a renderer, and outside `index.ts` so the screens stay ignorant of the store.
- `src/intro.ts`: startup animation helpers — `dissolveIn` (per-character shade-ramp dissolve for text) and `chunkyFadeIn` (stepped opacity fade). Driven by `setInterval`, need real renderable instances (not the `Box()`/`Text()` VNode factory proxies).
- `src/store/`: markdown-first persistence (Phase 0). Campaign data lives in `<campaignsDir>/<Campaign Name>/campaign.md` + `sessions/00N-slug.md`; saved one-shots in `<oneshotsDir>/<slug>.md`; reference PDFs in `<sourcesDir>/<System>/*.pdf`; settings in `~/.config/scribe/config.json` (`campaignsDir` default `~/Scribe`, `oneshotsDir` default `~/Scribe/One-Shots`, `sourcesDir` default `~/Scribe/Sources`).
  - `frontmatter.ts`: flat `key: value` frontmatter parse/serialize (no YAML).
  - `naming.ts`: folder-name sanitize, session-file slugify, collision-proof `uniqueName`. Regex classes use `\xNN` escapes — do not paste raw control chars into source.
  - `settings.ts`: `loadSettings()`/`saveSettings()` — creates config + campaigns/one-shots/sources dirs on first run, expands `~`. `defaultConfigDir()` honors `SCRIBE_CONFIG_DIR` (separate profiles; also how tests relocate the instruction files). `systemPromptOverride`/`oneshotPromptOverride` are config-file-only and deliberately absent from the settings screen.
  - `instructions.ts`: the user's optional instruction files (`~/.config/scribe/instructions.md` + `oneshot-instructions.md`) and `loadPromptOverride` for the core-replacement escape hatch. **Read-only — these files are never created.** That is the point: nothing is written to disk, so a user can never end up pinned to a stale copy of a prompt they never edited, and prompt changes made in code always ship. Missing/unreadable instructions read as `""`; a missing or blank override reads as `null` and falls back to the built-in core rather than leaving the agent with nothing.
  - `campaigns.ts`: `Campaign` type, `createCampaign`/`listCampaigns`/`loadCampaign`/`updateCampaignMeta`/`appendStorySoFar`. `campaign.md` body holds Background + The Story So Far sections.
  - `sessions.ts`: `Session` type, `createSession` (bumps campaign `nextSession`), `listSessions`, `setSessionStatus` (stamps dates), `trashSession` (soft-delete to `.scribe/trash/`).
  - `chat-log.ts`: conversation persistence per session+mode as JSONL in `.scribe/` (`loadChatLog`/`saveChatLog`/`clearChatLog`) — resumes planning/report chats across app sessions.
  - `sources.ts`: the source-document library (Phase 6) — PDF text extraction, caching, and keyword search. Layout is `<sourcesDir>/<System>/Book.pdf` with the cache alongside it in a **visible** `extracted/` folder (`extracted/book.md`), so the folder the user browses stays uncluttered but nothing is hidden from them. Loose PDFs directly in `<sourcesDir>` are filed under the synthetic system `"Unsorted"`. Cache files are ordinary frontmatter + a body of `<!-- page N -->`-marked text — no JSON index, no new format. Staleness is `size` + `mtime` vs. the PDF, so re-indexing a warm library is a `stat` per file. Slugs are unique across the **whole** library (not per folder) because `readSourcePages` resolves them globally. Search is BM25-lite over pages with a co-occurrence bonus, capped at 3 hits per document; page reads are clamped to the document and to a 10-page span so one call can't dump a book into context. **This is the only module allowed to import `unpdf`** — keeping the PDF dependency in one file is what keeps the rest of the app dependency-light. A PDF that fails to parse is skipped silently rather than throwing.
  - `oneshots.ts`: `saveOneshot(dir, { title, system?, content })` — writes one-shot plans as `<slug>.md` (frontmatter: title/system/created) with numeric collision suffixes; used by the `save_session` tool.

## Gotchas

- The app is an interactive TUI. Running it in a non-TTY or automated context may fail or hang.
- `bun run` without a script name is not configured; use `bun run src/index.ts` or `bun src/index.ts`.
- Key names: the main Enter key reports `key.name === "return"`; the keypad Enter is `"kpenter"` (not `"enter"`, which OpenTUI never emits as a `key.name`). Anything that acts on Enter must accept **both**. Escape is `"escape"`, Tab is `"tab"` (check `key.shift` for Shift+Tab).
- Headless testing: use `createTestRenderer` + `createMockKeys` from `@opentui/core/testing`. The test script MUST live inside the project — if run from outside, Bun resolves a second copy of `@opentui/core` from its global cache and rendering silently breaks (boxes draw, text never paints).
- Global `keypress` handlers on `renderer.keyInput` run **before** renderable (focused-widget) handlers, and `key.preventDefault()` in one stops the focused widget from ever seeing that key. That's the whole mechanism behind key borrowing: a screen's single listener can hand Enter to the completion popup or Escape to the question widget without a keymap system, and by *not* claiming a key it lets the focused textarea type as normal.
- `visible = false` sets the Yoga display to `none` — the renderable collapses out of the layout (siblings close the gap) and is blurred if focused. That's how the prompt yields its slot to the question widget: hidden, not disabled.
- To float a panel above a box, make it an absolutely positioned child of that box with `bottom: "100%"` — its bottom edge lands on the parent's top edge, re-anchoring itself whenever either changes height, with nothing to measure or poll, and overlaying its siblings rather than displacing them. Absolute offsets resolve against the parent's *padding* box, so `left: -1` is what puts a child's left border back over the parent's border column.
- An agent turn outlives the screen — the user can leave mid-stream or mid-question. `dispose()` destroys the `SyntaxStyle` every transcript row is built from, so anything a finishing turn touches on the way out must be guarded by the screen's `disposed` flag or it throws "NativeSyntaxStyle is destroyed". Covered by "leaving while a turn is in flight does not throw" and "leaving mid-question doesn't strand the turn" in `tests/chat.test.ts`.
- `MarkdownRenderable` must always be created with `streaming: true`, and never toggled back off. It only builds a synchronous first paint (`initialStyledText`) while streaming is on; with it off, every block waits on an async tree-sitter highlight and paints blank for a frame. Turning it off also rebuilds every block, so a `true -> false` flip blanks the whole transcript for a frame. Settled output is identical either way. Covered by the "markdown never blanks out" tests in `tests/chat.test.ts`.
